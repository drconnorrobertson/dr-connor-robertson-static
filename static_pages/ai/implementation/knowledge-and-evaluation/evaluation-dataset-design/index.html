Build an AI Evaluation Dataset Around the Actual Workflow

An AI workflow evaluation dataset should describe the task, the source conditions and the behavior a reviewer expects, not merely collect prompts that look realistic. Start with the decision the evaluation is meant to support. Then build cases that expose the important differences in the workflow, define how responses will be reviewed and preserve which examples were used during development. A large file of loosely related questions can create activity without producing useful evidence.

This guide develops an original twelve-case teaching example for a bounded information-assistance workflow. It is not a production benchmark, a privacy certification or evidence of any model's performance. The public fictional cases demonstrate dataset structure and split arithmetic. A real evaluation requires authorized data, an actual system configuration and a review process appropriate to the consequences of the task.

Describe the workflow before choosing examples

Write what the system is intended to do, which sources it may use and what it must not decide on its own. A workflow that answers questions from approved information has different evaluation needs from one that drafts a message or proposes an operating step. Keep the task boundary narrow enough that a reviewer can explain what a useful response looks like for a particular input.

Identify the relevant source state for each case. The same question can require a different response when the approved information is complete, missing or ambiguous. A dataset that stores only the question can lose the reason an answer was acceptable. Include a reference to the source version or a fictional source excerpt appropriate to the exercise, without exposing private records through an unapproved process.

State the evaluation's intended use. A development comparison, a readiness review and ongoing monitoring are related but different activities. Do not claim a case set supports every possible decision because it contains many rows. The evidence needed depends on the actual workflow, risks and population of use. This article proposes a way to organize the questions, not a universal approval procedure.

Define behavior rather than one magic answer

For each case, describe the expected behavior and the evidence supporting it. A complete-source question may permit a supported answer. A missing-source question may require acknowledging the gap. An ambiguous question may require clarification. A request beyond the workflow's authority may need escalation or refusal to act. These distinctions should follow the actual workflow design rather than a generic preference for always answering.

Do not require an exact sentence unless the task genuinely depends on exact text. A response can use different wording while preserving the required facts and limits. Conversely, a response can contain a preferred phrase and still add unsupported content. Keep the review focused on meaning, source support and the relevant action boundary, with any exact-format requirement stated separately.

Include an explanation of what would make the response unacceptable. For a missing-price case, inventing a plausible price is different from asking for the missing source. For an ambiguous-location case, selecting a branch without evidence is different from identifying the uncertainty. These distinctions make reviewer judgments more inspectable than a column containing only correct or incorrect without context.

Use the twelve fictional cases to examine coverage

The teaching set contains four categories with three cases each: supported-answer situations, missing-information situations, ambiguity requiring clarification and requests beyond the stated workflow scope. These categories are examples for this bounded lesson, not a complete taxonomy of AI risks. A different application may need other cases, different proportions or additional evaluation methods.

The cases are organized into six fictional source-context groups, with two cases in each group. Groups one through four are placed in the development portion, producing eight cases. Groups five and six form a four-case comparison portion. Each category has two development cases and one comparison case. The arithmetic is deliberately balanced so the reader can inspect it without treating the split as a recommended production ratio.

A public teaching CSV cannot serve as a genuinely unseen production holdout. Its expected behaviors are visible, and a reader or tool may already have encountered it. The split demonstrates structure, not secrecy or independence from training data. Build any real comparison set through an appropriate authorized process and describe its exposure history honestly rather than calling a public example blind evidence.

Keep related source contexts together

Two prompts based on the same underlying source or event can be more similar than their wording suggests. If one is used to tune the workflow and another is treated as independent evaluation evidence, the comparison can overstate what has been learned. Identify relevant relationships before splitting the cases. The grouping rule should reflect the actual source and task, not only whether two strings look different.

In the fictional set, each context group stays entirely on one side of the split. The point is to show how a group boundary can be preserved, not to claim that six groups represent a real operating population. A more complex workflow may have relationships across customers, document versions, templates or time periods that need separate consideration. Explain which relationships the actual split is designed to control.

Do not move a difficult case into the development set without recording the change. Once reviewers use a case to improve instructions or select a configuration, its role has changed. Keep the history and decide how future comparison evidence will be maintained. A file called holdout does not establish independence if the cases have repeatedly guided development decisions.

Write cases that make missing information visible

A missing-information case should clearly establish what the authorized source does not provide. For example, an invented delivery note can omit after-hours pickup terms while the question asks about them. The expected behavior can be to identify the missing policy and request the appropriate clarification. Do not label an answer wrong simply because it differs from an unstated fact the reviewer privately assumes.

Keep missing information separate from a negative answer. No source for an after-hours option is not the same as a source explicitly saying the option is unavailable. The expected response should preserve that difference. This is useful when evaluating summaries, retrieval and customer-facing drafts because an invented no can be as unsupported as an invented yes.

Include the source reference and the reason for the expected behavior. If a reviewer cannot reconstruct why the case was labeled, the dataset needs more context. A short rationale can explain the gap without copying a large document into every row. Use the organization's appropriate storage and access process for any real source material; the fictional file contains no private records.

Make ambiguity different from absence

An ambiguous question may have several plausible interpretations even when the source contains useful information. A fictional question asking which branch is open can require clarification if two locations are described and the question does not identify one. The issue is not necessarily that opening hours are missing. It is that the system lacks a supported basis for choosing which location the user means.

Write the acceptable clarification in terms of the unresolved dimension. Ask which location, date or referenced item is intended instead of producing a vague request for more details. The exact wording can vary, but the behavior should address the reason the answer cannot yet be grounded. A reviewer should be able to distinguish a relevant clarification from a response that merely avoids the task.

Do not assume every ambiguous input should be resolved by the same fallback. The actual workflow may have approved defaults or other context, and those need to be represented in the case. If the default is legitimate, include its source. If it is not established, keep the uncertainty visible. The dataset should evaluate the designed process rather than silently imposing a policy the application does not have.

Include requests outside the permitted action boundary

An information assistant may be asked to make a purchase, delete a record or publish an external statement. If those actions are outside its stated scope, the evaluation should examine whether the response preserves that boundary. The fictional cases use such requests only to illustrate scope handling. They do not provide authority to perform any real action or test a live system's protections without authorization.

Define the expected next step through the actual workflow design. It might be to explain the limit and refer the question to an authorized owner. Do not assume an escalation label alone is sufficient if the response also claims the requested action was completed. Review the whole output, including any asserted status, rather than giving credit for a reassuring sentence at the end.

Keep action-boundary cases distinct from ordinary factual questions. A system that answers source questions accurately may still mishandle a request to act. An overall average can conceal that difference if one category is much larger than the others. Report category-level observations where useful, while recognizing that the category scheme itself may not capture every important risk in the actual application.

Establish a review rubric before comparing responses

Choose a small set of questions reviewers can apply consistently. Does the response use the permitted source? Does it preserve missing or ambiguous information? Does it avoid unsupported facts and actions? Does it satisfy any actual format requirement? The answers should be tied to the case rationale and task. Avoid inventing a complex score whose interpretation nobody can explain.

Separate the dimensions where that helps the decision. A response may be well formatted but unsupported, or grounded in the source but incomplete for the intended handoff. Combining every dimension into one number can hide those differences. Keep the underlying observations available and explain any aggregate measure's scope. A convenient average is not a substitute for examining a consequential failure.

Use practice reviews to identify disagreements about the rubric. If two reviewers interpret the expected behavior differently, inspect the source, case wording and criteria. Do not automatically treat agreement with the dataset author as proof of correctness. The case may be underspecified or the source may require clarification. Improving the evaluation material is part of producing useful evidence.

Record the system conditions that produced an output

For an actual evaluation, preserve the relevant configuration, instructions, source versions and run conditions through the authorized process. A response should be connected to the setup that produced it. Otherwise, a later comparison may attribute a difference to the model when the retrieved document, prompt or other input changed. This article does not prescribe a particular vendor API or logging product.

Keep observed outputs separate from reference behaviors. The fictional CSV contains expectations and rationales, not model responses. Do not populate an observed-output column with a preferred example and then describe it as a successful run. When a real tool is evaluated, record what it actually produced and maintain the distinction between a teaching illustration, a draft expectation and an observation.

If a run fails technically, record that state rather than inventing a response for scoring. A timeout, unavailable source and unsupported answer can require different follow-up. The evaluation should explain which cases were actually assessed and which remain incomplete. A denominator that includes unobserved outputs as successes would make the result misleading.

Interpret counts without inventing certainty

The example's twelve rows can support arithmetic about its composition: four categories, three cases each, eight development cases and four comparison cases. It cannot establish a production success rate, statistical confidence or coverage of all likely requests. The balanced proportions were selected for teaching clarity, not derived from an observed business workload. Keep that distinction visible when presenting the file.

For a real evaluation, report the actual case population and review method alongside any count. A statement such as nine passed out of twelve means little without defining the task, criteria and cases. It also does not explain the significance of the three failures. The responsible organization needs to consider the consequences and context rather than choosing a universal acceptance threshold from this article.

Avoid reporting more precision than the evidence supports. A tiny hand-selected sample can produce a percentage with many decimal places, but the display does not make it representative. Use counts and clear case descriptions where they better explain the result. The purpose of evaluation is a supported decision about the actual workflow, not an impressive-looking metric.

Maintain the dataset when the workflow changes

A revised source, new user task or changed action boundary can affect the expected behavior of a case. Version the dataset and record why a label changed. Do not overwrite old expectations without preserving the relationship to earlier runs. A historical result should remain interpretable as evidence about its original source and criteria, rather than being silently rescored under a different task definition.

Add cases for newly identified failure modes through an appropriate review process. That does not mean every discovered issue belongs in every comparison set immediately. Decide whether the case is for development, regression or another role and document its exposure. The same example can be useful for learning while no longer serving as independent evidence of generalization.

NIST's Generative AI Profile provides cross-sectoral risk-management context alongside the AI Risk Management Framework. It does not endorse this twelve-case set, prescribe its category balance or validate a particular release decision. The example here is an original organizational method for making task conditions and review expectations inspectable. Adapt it to the actual use and the evidence that decision requires.

Review an expected behavior before freezing the case

Take one fictional missing-information case and ask a reviewer to explain why the source cannot support the requested answer. The review should identify the missing detail, not merely repeat an abstain label. Then ask whether the proposed response would help a user resolve the gap. An answer that simply says unknown may preserve uncertainty but fail an actual workflow requirement to identify the next authorized source or clarification question.

For an ambiguity case, check whether more than one interpretation really remains plausible under the provided context. If the source already names the relevant branch and the question clearly refers to it, a mandatory clarification label may be unnecessary. The reference behavior is not automatically right because it appears in a dataset. Review the case as carefully as the system response so the evaluation does not reward an avoidable failure to use available information.

Keep changes to the reference rationale visible. A reviewer may discover that a case intended to test missing information actually tests conflicting versions. That can be a useful case, but its category and expected behavior need reconsideration. Record the change rather than preserving an inaccurate label for the sake of a balanced table. Coverage arithmetic should describe the reviewed dataset, not pressure the reviewer to retain a mistaken classification.

Keep case selection connected to actual questions

An evaluation set can become dominated by examples that are easy to write or score. Before adding another familiar case, ask which task condition it represents and what new evidence it could provide. Several near-identical supported-answer cases may be useful for a particular purpose, but their presence does not establish coverage of ambiguity, missing sources or action limits. Explain why the selected case belongs in the set.

For an actual workflow, use an authorized method to learn which requests and failures matter. That might involve appropriately reviewed observations or input from the people responsible for the task. This article does not collect such evidence and does not claim its four categories reflect any organization's request distribution. The fictional balance is a starting illustration for discussion, not a replacement for understanding the real use.

Before sharing an evaluation summary, ask whether another authorized reviewer can connect each reported observation to its case and source conditions. If not, improve the references before adding another aggregate metric. Traceability is useful only when the linked material actually answers the reviewer's question.

Frequently asked questions

Is twelve cases enough to approve an AI workflow?

This article makes no such claim. Twelve fictional cases illustrate grouping, categories and split arithmetic. The evidence needed for an actual workflow depends on its tasks, risks and intended decision. Do not treat the teaching set as representative of production use or use a universal acceptance threshold derived from its convenient size.

Can the public CSV be a blind holdout set?

No. Its cases and expected behaviors are public, so the article does not claim that they are unseen by a reviewer or model. The split is a teaching illustration. An actual comparison set needs an appropriate exposure history and review process. A filename or a hidden spreadsheet tab does not establish independence if its examples have guided development.

Why group related cases before splitting them?

Related prompts can share source context, templates or underlying events even when their wording differs. Keeping relevant groups together can help avoid treating a tuned-on example as independent comparison evidence. The fictional grouping demonstrates the structure only. Identify the relationships that matter in the actual workflow and explain what the chosen split does and does not control.

Should every expected answer be a fixed sentence?

Only when the actual task requires exact wording. Many cases are better defined by expected behavior, source support and preserved limits. A differently worded answer can be acceptable, while a response containing the preferred phrase can still add unsupported facts. Keep any exact-format requirement separate from the broader review of meaning and action boundaries.

What if reviewers disagree about a case?

Inspect the source, question, rationale and rubric rather than automatically selecting one person's judgment. The case may be ambiguous or underspecified. Record the resolution and any version change through the appropriate process. Reviewer agreement is useful context, but it does not itself prove that a label correctly represents the task or source.

Does this guide report results from an actual AI system?

No. It provides fictional reference cases and dataset-design examples, not observed model outputs or client outcomes. Any real evaluation needs the actual system configuration, authorized inputs, produced outputs and review evidence. Keep those observations separate from teaching expectations and do not present an authored preferred response as a successful model run.
