Compare AI Releases with Paired Cases, Missing Results and Explicit Gates

Preserve version scope, case transitions and incomplete results when reviewing an AI release, using an original fictional twenty-case comparison.

Published October 24, 2026 · Expanded October 26, 2026 · Website editorial

Treat a change as a comparison of versions

Changing an AI model can change a workflow even when the user interface stays the same. A prompt edit, source revision, retrieval configuration or tool contract can also alter behavior. A useful regression comparison therefore identifies the complete baseline and candidate configurations, rather than attributing every difference to a model name. Start with the actual task, the behavior you intend to preserve and the change you want to examine. Keep the release question narrower than whether one system is better at everything.

This expanded playbook uses an original fictional table of assigned pass and fail labels. The labels were deliberately written to illustrate paired comparison arithmetic. They are not observed outputs from any model, a benchmark, a client project or evidence that a workflow is reliable. No model calls were made to create the examples. Reproducing the table's arithmetic checks the explanation, not an AI product. The page provides a method for preparing a real comparison while keeping the absence of real evaluation evidence explicit.

NIST's AI RMF Core describes documenting test and evaluation methods, metrics and limitations within its Measure function. That is useful context for a release discussion, not a certification supplied by this article. The framework is voluntary and context dependent. Use the relevant responsible people and requirements for your actual system. This page does not turn a worksheet, a target score or a successful build into proof of safety, legal compliance, appropriate access or permission to act on external systems.

Freeze the task definition before comparing results

Write the input boundary, expected output and evaluation rubric before reviewing candidate results. A fictional extraction task might require preserving an explicit date, reporting missing information and avoiding unsupported additions. Those are different criteria from producing fluent prose. State what counts as a pass, which failures need separate treatment and how ambiguous cases will be handled. A rubric should be clear enough that another reviewer can understand the expected behavior without guessing what the first reviewer had in mind.

Record the prompt version, model identifier as actually supplied, relevant settings, source snapshot and tool contract version for both configurations. If a provider does not expose or guarantee a stable underlying version, document that limitation rather than inventing reproducibility. If the candidate changes several components, the comparison concerns that package of changes. It does not isolate the causal effect of one component. Separating components in later experiments may help explain a difference, but that is a separate comparison with its own record.

Preserve the evaluation cases and their expected behavior as a versioned set. An edited expected answer can change a score even when neither system output changes. If an expectation was wrong, correct it openly and apply the correction consistently to the comparison. Keep the prior version available for explanation. A record that quietly rewrites expectations to fit the candidate cannot support the same interpretation as a comparison made against a definition established independently of those candidate outputs.

Pair results by stable case identity

A paired comparison asks what happened to the same case under the two configurations. Use a stable case identifier and retain the connection to the original input and expected behavior. Do not pair rows by their position after sorting, by a shortened question that is not unique, or by a similar-looking output. A missing case and a duplicate case can change the apparent total while leaving a spreadsheet visually convincing. Check uniqueness and membership before calculating scores or describing improvements.

In the original teaching file, cases C01 through C20 have assigned baseline labels, and the candidate column intentionally has two blanks. The first eighteen have labels in both columns. Those eighteen are the paired comparison set for the simple pass-rate calculation here. The other two remain visible as missing candidate labels. The file does not say whether a real missing result would reflect a timeout, a review backlog or an execution failure; no such event occurred in creating these invented entries.

A real evaluation should distinguish an output that explicitly fails a rubric, an output that was never produced, an output that has not been reviewed and a case excluded under a stated rule. These statuses can require different operational treatment. Do not silently make them all passes or delete them. A release policy may choose a conservative rule for incomplete cases, but label that policy choice separately from the observed result. This page supplies no universal rule for approving an incomplete comparison.

Reproduce the original twenty-case teaching example

The authored example contains ten paired cases labeled pass in both versions, four labeled fail in the baseline and pass in the candidate, three labeled pass in the baseline and fail in the candidate, and one labeled fail in both. Those counts sum to eighteen paired cases. C19 and C20 are baseline pass with the candidate label missing. They remain part of the intended twenty-case file, but they are not silently included in a denominator that requires two available labels.

Within the eighteen paired cases, the baseline passes thirteen: the ten shared passes plus the three regressions. The candidate passes fourteen: the ten shared passes plus the four improvements. The paired pass fractions are thirteen eighteenths and fourteen eighteenths. The candidate is ahead by one passing case, or one eighteenth of the paired set, approximately 5.56 percentage points. This is a descriptive difference in a deliberately authored file, not an estimate of population performance or a claim of statistical significance.

Across all twenty baseline entries there are fifteen passes, because the two cases with missing candidate labels also have baseline pass. Fifteen out of twenty is 75 percent. Comparing that baseline percentage directly with fourteen out of eighteen for the candidate would mix coverage. It obscures which cases were available in each column. Show the twenty intended cases, eighteen paired cases and two missing candidate labels alongside the paired result. Keep a complete-set report distinct from a paired-subset calculation.

Keep improvements and regressions visible together

The net increase of one passing case is four improvements minus three regressions. A summary that reports only the net change hides seven cases whose assigned status changed. The regressions are not explained away by the improvements; they identify behavior to inspect. In a real workflow, those case-level differences may reveal a new failure mode, a rubric problem or ordinary variability. The fictional labels cannot establish which explanation applies, but they demonstrate why retaining case identity is useful.

The paired transition table has four cells: baseline pass to candidate pass, baseline fail to candidate pass, baseline pass to candidate fail and baseline fail to candidate fail. Name the direction of each cell. Swapping the version labels reverses the meaning of improvement and regression without changing the numbers in the file. Before publishing a summary, read its statement back against at least one original case from each occupied cell. This catches an interpretation error that a correctly summed total alone would miss.

The authored file marks C15 as a critical-category case. It is one of the three regressions. That category is an invented teaching designation, not an assertion that any real system caused harm. Its purpose is to show that an aggregate improvement does not decide a critical-case question. Define relevant categories and decision rules for your actual task before inspecting results. Do not label a convenient failure critical only after the fact to create a desired conclusion, or remove a critical label merely to make a candidate easier to release.

Do not let missing cases disappear into a favorable denominator

If a report says the candidate passed fourteen of eighteen reviewed cases, it should also say that two of the twenty intended candidate cases lack a label. The reader needs both facts. Available-case reporting can be useful, but it must not imply complete evaluation. Missingness can be related to difficult inputs in a real run, so the available subset may differ systematically from the intended set. The teaching file supplies no mechanism or statistical model that would justify generalizing from its available rows.

For a separate arithmetic scenario, suppose the two missing candidate labels were later assigned fail. The candidate would then have fourteen passes out of twenty, or 70 percent, against the baseline's fifteen out of twenty. If they were both assigned pass, the candidate would have sixteen out of twenty, or 80 percent. Those are hypothetical bounds under two different completions of our binary-label exercise. Neither completion is an observed result or a recommendation to replace unknowns with the more convenient value.

Do not count the two hypothetical completions as additional evaluation runs or additional independent cases. They are alternative ways to complete the same authored file. Their purpose is to make the dependence on missing information visible. A real report should identify the responsible follow-up, preserve the incomplete status and explain any decision made before resolution. An operational owner might postpone a change or limit its scope, but that decision requires the actual workflow's context and authority rather than an automatic inference from this page.

Compare categories without hiding their size

A category summary needs its numerator, denominator and definition. One critical regression out of one critical case in our authored table is very different coverage from three regressions among eighteen paired cases overall. Neither count estimates how often a real critical error occurs. A small category can be operationally important while supplying little evidence about a broader rate. Keep category-level exceptions visible without presenting tiny sample percentages as precise estimates of production behavior or ranking systems across unrelated tasks.

Categories can overlap. A case may be long, involve a date and concern an approval boundary at the same time. If you count it in each relevant slice, explain that the slice counts are not mutually exclusive and should not be added as though they were distinct cases. If you need mutually exclusive groups for an additive report, define that grouping deliberately. A table can support both views, but they answer different questions. Preserve the case-level source so readers can understand the aggregation.

Do not infer fairness, language coverage, accessibility or suitability for a user population from a handful of invented category labels. Those are separate assessment questions requiring appropriate data, methods and context. The example's critical flag is only a device for explaining release gates. The useful habit is to ask what a summary hides and which important conditions are absent, not to attach an assurance label to every slice of a small worksheet.

Separate rubric changes from system changes

Sometimes reviewers disagree because the expected behavior is underspecified. One reviewer may accept a concise paraphrase while another requires preserving an exact qualifier. Retain the original output, the rubric version and the reason for disagreement. Resolve the criterion through the appropriate process before treating the difference as evidence that the candidate improved or regressed. If the rubric changes, apply it consistently to relevant baseline and candidate material or state clearly that the two scores are no longer directly comparable.

Human judgment and automated checks can cover different parts of a task. A deterministic parser can check a required field's presence, while a factual-support review may require examining the source and claim. Passing a structural check does not establish truth or completeness. Conversely, a readable answer can fail a required format needed by a downstream system. Keep the actual checks and their limits explicit. Do not use a single pass label to imply that every aspect of a workflow was evaluated when only one criterion was checked.

If an AI judge helps assign labels in a real evaluation, record its version, instructions and validation approach. Its labels are evaluation outputs, not unquestionable ground truth. This guide's labels were authored manually for arithmetic and do not demonstrate judge agreement, model accuracy or reviewer reliability. Use independent evidence suitable to the actual criterion when deciding how much confidence to place in a scoring process. A persuasive explanation of a score is not a substitute for a supported scoring method.

Protect the distinction between development and evaluation

The scikit-learn common-pitfalls documentation explains data leakage in supervised learning and warns against using test data to make model choices. The analogous practical question for a prompt workflow is whether the cases used to revise the prompt are later described as untouched evidence. Those are different roles. Repeatedly inspecting the same cases and tuning to their failures can make that set useful for development while reducing the strength of a claim about unfamiliar cases. State the set's actual role and history.

Keep development cases separate from any held-out evaluation intended to answer a generalization question. When a case is exposed during debugging, document that exposure rather than pretending its status never changed. The right split depends on the task and data relationships; this guide supplies no universal proportion, minimum sample size or leakage detector. Closely related documents or duplicated cases can also make a nominal split less informative. Preserve grouping information where it matters instead of assuming a random row split resolves every dependence.

A regression set can still be valuable even when the team knows its cases well. It can catch behavior that was previously supported and later lost. Describe that purpose honestly. Do not rewrite a known regression set as proof of novel-task performance. If you add new cases after discovering a failure, version the set and identify when the new case entered. Reporting both the prior set and the expanded set can preserve the distinction between comparable historical checks and a broader newly defined assessment.

Keep cost and latency alongside quality, not inside an unexplained score

A real release comparison may include elapsed time, model usage, retries, tool calls and review effort. Define each measurement and its boundary before summarizing. Does latency end when an initial answer appears or when a usable result is complete? Does cost include retries and failed attempts? Are prices historical observed charges or estimates under a stated schedule? The fictional CSV contains none of those measurements, so it cannot support a claim that the candidate is faster, cheaper or more productive.

Avoid adding unlike quantities into a composite score without explaining the weights and decision rule. A small reduction in an estimated cost does not automatically compensate for a critical failure. A faster answer that needs additional correction may not shorten the full workflow. Keep the quality gates, operating measurements and unresolved questions visible as separate evidence. If the organization chooses a tradeoff, identify who made it and under what constraints rather than presenting the arithmetic as an authorization that made the decision itself.

Model behavior can vary between runs, and system components can change outside a simple prompt edit. If repeated runs are part of the real plan, state how many, how they are grouped and how results will be summarized. Repetitions of one input are not automatically equivalent to many independent task cases. Our twenty-case file contains one authored label per version slot and no run-to-run observations. It therefore supplies no variance estimate, reliability interval or claim about repeatability of any deployed service.

Connect the report to a bounded decision and recovery path

A useful release report links the exact candidate configuration to the actual evidence, unresolved cases and decision owner. It explains what remains outside scope and what would cause a pause or rollback. A rollback path should identify the prior configuration and dependencies that need to be restored; merely naming an old model is not enough if prompts, sources or tool contracts also changed. This page describes the planning question and does not execute a deployment, restore data or establish that a rollback will work.

If a limited rollout is authorized, specify its audience, duration, monitored behavior and stop conditions through the real release process. Avoid using the phrase limited rollout as a vague substitute for defining the boundary. Observe the full workflow within its actual permissions and keep the ability to stop external actions where relevant. Offline case scores alone do not grant access, approve messages, create records or authorize financial or operational actions. Consult the separate tool-contract and approval playbooks for those distinct implementation concerns.

For the teaching file, the defensible conclusion is narrow: eighteen paired authored labels show four improvements and three regressions, including the designated critical case, while two candidate labels remain missing. The net paired pass count is higher by one. No release decision follows from those invented values. Use the structure to prepare a real comparison with genuine inputs, supported labels, appropriate review and an accountable decision, without presenting a practice worksheet as evidence that the actual system has passed.

Frequently asked questions

Does a higher paired pass rate mean every behavior improved?

No. The fictional candidate has fourteen passes versus thirteen on the eighteen paired cases, yet three baseline passes become candidate failures. Retain the transition counts and case identities alongside the net change. The example illustrates arithmetic only; it does not measure any model, demonstrate significance or establish suitability for a real workflow.

Should missing candidate labels be removed from the report?

Keep them visible with a defined status. You can calculate an explicitly labeled available paired subset, but disclose the intended set and missing count. Do not silently compare denominators from different coverage. Any rule treating incomplete cases conservatively belongs to the real evaluation policy and should be distinguished from an observed pass or fail.

What if a prompt, source and model all change together?

Describe the candidate as that package of configuration changes. A paired comparison can show differences between the two packages under the defined evaluation, but it does not isolate which component caused them. Preserve the component versions and use separate controlled comparisons if you need evidence about an individual change's contribution.

Can I keep revising a prompt against the same test cases?

Those cases can remain useful for development or known regression checks, but describe their role honestly. Do not call repeatedly inspected tuning cases untouched evidence about unfamiliar inputs. Preserve exposure and dataset versions, and plan any separate held-out assessment according to the actual task rather than assuming this article supplies a universal split or sample size.

Does an aggregate improvement override a critical regression?

Only the actual predefined decision rules and responsible process can determine a release outcome. The fictional critical flag demonstrates why a net average cannot answer every case-level question. This page does not supply a risk tolerance, approval threshold, compliance determination or permission to deploy a system that fails an important behavior.

Are the downloadable labels actual evaluation results?

No. All twenty cases and labels are deliberately authored teaching entries. No model was run, no client data was used and no professional review or product endorsement is asserted. Independent arithmetic checks verify the example's counts and fractions, not AI quality, safety, business outcomes or the readiness of any real release.
